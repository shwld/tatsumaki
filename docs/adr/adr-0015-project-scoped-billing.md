## Context

[ADR-0011](adr-0011-open-registration-free-plan.md) は公式ホスト版の Pro をユーザー単位で扱った。課金アカウントはユーザーで、Pro かどうかは所有プロジェクト数の上限(`maxOwnedProjects`)を作成時に比べるだけだった。解約や未払いでも、止まるのは新規作成だけで、既存データは編集もエクスポートもできた。

この形では、1 人が契約すれば何個でもプロジェクトを所有でき、支払いが止まっても利用は続けられる。料金をプロジェクトの価値に合わせ、未払いのプロジェクトを止められるようにするため、課金の単位をプロジェクトに変える。

- 設計案: `tm artifact get --project 01KN9P32R248P2PK1413DKQQG5 01M6WCSQ7K9PBXXF5W925860FB`(プロジェクト単位の Pro 課金 — 設計案 v1、2026-11-08 時点の合意)

セルフホスト版(`ENTITLEMENT_MODE` 未設定)はこの ADR の対象外で、これまでどおり `UnlimitedEntitlementProvider` が制限をかけない。

## Decision

### 課金の単位と料金

- 1 プロジェクトにつきサブスクリプション 1 つ。プロジェクトを 2 つ所有するなら 2 つ契約する。料金は 1 プロジェクトあたり月額 3,500 円(税込か税抜かは未決)。
- メンバーとしての参加は無料・無制限。有料なのはオーナーとして所有するプロジェクトだけ。
- Pro の所有上限はない。契約した数だけ所有できる。所有数の上限による判定はなくなる。
- 契約していないユーザーはプロジェクトを所有できない(ADR-0011 の participate-only と同じ意味)。
- 課金の契約は Stripe の customer ではなくプロジェクトに付く。customer は購入したユーザー単位のまま。公開側の `EntitlementProvider` の契約は、ユーザーの権利ではなくプロジェクトの状態を返す形に変わる。

### プロジェクトの状態

プロジェクトの状態は `active` / `grace` / `suspended` の 3 つ。

| 状態 | Stripe の購読 | 編集 | 閲覧 | エクスポート | 表示 |
| --- | --- | --- | --- | --- | --- |
| `active` | `active` / `trialing` | 可 | 可 | オーナーのみ | なし |
| `grace` | `past_due`(猶予期限まで) | 可 | 可 | オーナーのみ | 支払い失敗と期限をオーナーに表示 |
| `suspended` | 猶予切れ、`canceled` / `unpaid` / `paused` / `incomplete` / `incomplete_expired`、購読なし | 不可 | 可(全メンバー) | 不可 | 全メンバーに読み取り専用、オーナーに再開の導線 |

- Control Plane(非公開)の ADR-0002 から、次の判定を継承する。tatsumaki の Pro Product の購読だけを対象にすること。webhook のスナップショットではなく、Stripe の現在状態から照合すること。
- 変更点は 2 つある。ユーザー単位の Pro / Free × active / grace / restricted を、プロジェクト単位の 3 状態にする。購読なしは Free / active ではなく `suspended` にする。
- `suspended` では、Web・API・MCP・CLI の書き込みをすべて拒否する。エクスポート API も拒否する。
- エクスポートは状態にかかわらずオーナーだけに許す。現在のエクスポート権限がこれと一致しているかは、停止状態を強制する story で確認する。

### 停止中のデータ

- 削除しない。非表示にもしない(読み取りはできる)。
- 同じプロジェクトを再購読すれば `active` に戻る。エクスポートは再開した後にオーナーが行う。
- 保持期限を設けるかは未決。

### 作成と譲渡

- 作成では、プロジェクト ID を先に払い出し、そのプロジェクトを対象に購読する。権利が `active` になってから、プロジェクトの行を作る。支払いを終えずに離脱しても、作成途中のプロジェクトは残らない。
- 所有権を譲渡するときは、受け手が同じプロジェクトを対象に購読し直す。受け手の購読が `active` になってからオーナーを切り替え、元の購読を解約する。
- 1 つのプロジェクトに購読が一時的に 2 つある間(譲渡中)は、どちらか 1 つが `active` / `trialing` なら `active` とする。これは暫定のルールで、課金の重なりの扱い(未決 2)と合わせて見直す。

### Control Plane 障害時

- 公式ホスト版(`ENTITLEMENT_MODE=control-plane`)では、プロジェクトの状態が分からないとき、作成・書き込み・エクスポートを HTTP 503 で拒否する(fail closed)。障害の間に停止中のプロジェクトを編集・エクスポートできてしまうと、停止の強制が抜けるため。
- 読み取りは続ける。閲覧はどの状態でも許されるので、状態が分からなくても結果は変わらない。
- 停止状態を強制する story が出るまでは、ADR-0011 の挙動のままになる。権利を問い合わせるのは作成時だけで、Control Plane に届かなければ作成だけを 503 で拒否する。Control Plane の応答には cache の指定があるが、tatsumaki 側はまだキャッシュしていない。

## 未決事項

1. 税込か税抜か、インボイス。3,500 円を税込で示すか、Stripe Tax を使うか、適格請求書をどう発行するか。
2. 譲渡時の課金の重なり。元の購読を即時に解約するか期間末か、日割り返金をするか。購読が 2 つある間の権利判定は上記の暫定ルールで進める。
3. 停止中データの保持期限。無期限にするか、一定期間で区切るか。削除する場合の事前通知。
4. 既存プロジェクトの移行。有料化の時点で既に所有しているプロジェクトを無料のまま残すか、猶予を置いて契約を促すか。
5. 作成の失敗からの復旧。決済の完了後に tatsumaki 側の作成が失敗した場合の再試行と補償。
6. トライアル。初回の無料期間を設けるか。設けるなら `trialing` の画面表示。
7. 停止中のエクスポート拒否の法的な整理。GDPR 第 20 条(データポータビリティ)は本人の請求に基づく権利。日本の個人情報保護法の開示請求の扱いは未調査。利用規約に明記する前提。
8. プロジェクトの状態のキャッシュ。状態を操作ごとに見るので、キャッシュしなければ書き込みのたびに問い合わせが増え、Control Plane の可用性がそのまま書き込みの可用性になる。キャッシュするか、するなら有効期間と、障害時に古い値を使える期間を、停止状態を強制する story で決める。
9. 停止中に、オーナーがプロジェクトを削除できるか。メンバーが脱退できるか。書き込みの全面拒否をそのまま当てはめると、削除するには再購読が必要になる。未決 3・7 と合わせて決める。

停止中のエクスポートについての調査メモ: Trello と Atlassian(Jira)の公式ページでは、請求期間の末日まで有効で、データを削除せずに保持する扱いを確認できた。停止後にエクスポートできるかは、どちらの公式ページにも書かれていなかった。

## Consequences

- 判定が「作成時に所有数を比べる」から「操作ごとにプロジェクトの状態を見る」に変わる。プロジェクトに対する書き込み・エクスポートの経路はすべて状態を確認する必要があり、確認漏れがそのまま無料利用になる。
- 「購読なし = `suspended`」なので、既存の所有プロジェクトは購読を持たず、強制を有効にした時点ですべて停止する。停止状態の強制は、既存プロジェクトの移行方針(未決 4)が決まるまで本番で有効にしない。
- 停止中のエクスポート拒否は、利用規約に明記する(未決 7)まで本番で有効にしない。
- Control Plane の障害は、公式ホスト版の書き込みとエクスポートの障害になる。読み取りは続く。
- 解約や未払いは、そのプロジェクトのメンバー全員の編集を止める。オーナー以外にも影響するので、停止の理由と再開の方法を画面で示す。
- 所有上限の変数と `maxOwnedProjects` の判定は不要になる。置き換えは作成フローの story で行う。
- Control Plane の課金アカウントと Checkout / Portal は、プロジェクトの作成・再開・譲渡のための購入に作り替わる。
