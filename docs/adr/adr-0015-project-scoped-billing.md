# ADR-0015: 公式ホスト版の課金をプロジェクト単位にする

## Context

[ADR-0011](adr-0011-open-registration-free-plan.md) は公式ホスト版の Pro をユーザー単位で扱った。課金アカウントはユーザーで、Pro かどうかは所有プロジェクト数の上限(`maxOwnedProjects`)を作成時に比べるだけだった。解約や未払いでも、止まるのは新規作成だけで、既存データは編集もエクスポートもできた。

この形では、1 人が契約すれば何個でもプロジェクトを所有でき、支払いが止まっても利用は続けられる。料金をプロジェクトの価値に合わせ、未払いのプロジェクトを止められるようにするため、課金の単位をプロジェクトに変える。

- 設計案: `tm artifact get --project 01KN9P32R248P2PK1413DKQQG5 01M6WCSQ7K9PBXXF5W925860FB`(プロジェクト単位の Pro 課金 — 設計案 v1、2026-11-08 時点の合意)

セルフホスト版(`ENTITLEMENT_MODE` 未設定)はこの ADR の対象外で、これまでどおり `UnlimitedEntitlementProvider` が制限をかけない。

## Decision

### 課金の単位と料金

- 1 プロジェクトにつきサブスクリプション 1 つ。プロジェクトを 2 つ所有するなら 2 つ契約する。料金は 1 プロジェクトあたり月額 3,850 円(税込)。
- メンバーとしての参加は無料・無制限。有料なのはオーナーとして所有するプロジェクトだけ。
- Pro の所有上限はない。契約した数だけ所有できる。所有数の上限による判定はなくなる。
- 契約していないユーザーはプロジェクトを所有できない(ADR-0011 の participate-only と同じ意味)。
- トライアル(初回の無料期間)は設けない。購読と同時に課金が始まる。Stripe の `trialing` は判定では `active` と扱うが、専用の画面は作らない。

### 税と請求書

- 消費税の計算には Stripe Tax を使う。Price は税込(`tax_behavior=inclusive`)で作る。この設定は後から変えられない。
- 運営者は適格請求書発行事業者として登録済みで、Stripe の請求書を適格請求書として、領収書を適格簡易請求書として発行する。登録番号を Stripe の請求書設定に入れることを、本番の有効化の手順に含める。
- 根拠: [Stripe: 商品税コードと税金処理](https://docs.stripe.com/tax/products-prices-tax-codes-tax-behavior)、[Stripe: 適格請求書等保存方式](https://support.stripe.com/questions/planning-for-the-introduction-of-the-qualified-invoice-system)、[Stripe: 日本の請求書のベストプラクティス](https://stripe.com/en-lu/guides/best-practices-for-setting-up-invoicies-in-japan)

### 課金のモデル

| 対象 | 単位 | 紐づけ |
| --- | --- | --- |
| 課金アカウント(Stripe の customer) | ユーザー | 1 ユーザーにつき 1 つ。今の `billingAccountId = users.id` のまま |
| Product / Price | サービス全体で 1 つ(Pro) | プロジェクトごとに作らない |
| 購読(subscription) | プロジェクト | 購読 1 本が 1 プロジェクトの代金。どのプロジェクトの購読かを購読自体に持たせる |
| 権利(`active` / `grace` / `suspended`) | プロジェクト | そのプロジェクトの購読から導く |

- 1 人のユーザーが 2 つのプロジェクトを所有すると、customer は 1 つ、購読は 2 本になる。
- 設計案 v1 の version 2 までの比較表にあった「`billingAccountId = projectId`」は採らない(version 3 で修正済み)。customer はユーザー単位なので、課金アカウントをプロジェクトにすると、1 つの customer が複数の課金アカウントに属してしまう。プロジェクトに紐づけるのは課金アカウントではなく購読である。
- 公開側の `EntitlementProvider` の契約は、ユーザーの権利ではなくプロジェクトの状態を返す形に変わる。

### 新規機能として作る

- 公式ホスト版では、Pro の購入をまだ受け付けていない。ユーザー単位の契約も課金データも存在しない。
- そのため、ユーザー単位の契約との互換は持たせない。課金データの移行も考えない。
- 本体の既存プロジェクトは開発者自身のものだけなので、移行の仕組みは作らない。購読を持たないので、強制を有効にした時点で `suspended` になる。開発者は、有効化の前に自分のプロジェクトの扱いを手当てする。

### プロジェクトの状態

プロジェクトの状態は `active` / `grace` / `suspended` の 3 つ。

| 状態 | Stripe の購読 | 編集 | 閲覧 | エクスポート | 表示 |
| --- | --- | --- | --- | --- | --- |
| `active` | `active` / `trialing` | 可 | 可 | オーナーのみ | なし |
| `grace` | `past_due`(猶予期限まで) | 可 | 可 | オーナーのみ | 支払い失敗と期限をオーナーに表示 |
| `suspended` | 猶予切れ、`canceled` / `unpaid` / `paused` / `incomplete` / `incomplete_expired`、購読なし | 不可 | 可(全メンバー) | 不可 | 全メンバーに読み取り専用、オーナーに再開の導線 |

- Control Plane(非公開)の ADR-0002 から、次の判定を継承する。tatsumaki の Pro Product の購読だけを対象にすること。webhook のスナップショットではなく、Stripe の現在状態から照合すること。
- 変更点は 2 つある。ユーザー単位の Pro / Free × active / grace / restricted を、プロジェクト単位の 3 状態にする。購読なしは Free / active ではなく `suspended` にする。
- `suspended` では、Web・API・MCP・CLI の書き込みをすべて拒否する。エクスポート API も拒否する。
- 例外として、`suspended` でもオーナーはプロジェクトを削除でき、メンバーは脱退できる。どちらも利用を増やさず、本人がデータを消せるようにするため。
- エクスポートは状態にかかわらずオーナーだけに許す。現在のエクスポート権限がこれと一致しているかは、停止状態を強制する story で確認する。

### 停止中のデータ

- 削除しない。非表示にもしない(読み取りはできる)。
- 同じプロジェクトを再購読すれば `active` に戻る。エクスポートは再開した後にオーナーが行う。
- 保持期限は当面設けない(無期限)。容量が問題になった時点で、期限と事前通知を別の story で決める。

### 作成と譲渡

- 作成では、プロジェクト ID を先に払い出し、そのプロジェクトを対象に購読する。権利が `active` になってから、プロジェクトの行を作る。支払いを終えずに離脱しても、作成途中のプロジェクトは残らない。
- 所有権を譲渡するときは、受け手が同じプロジェクトを対象に購読し直す。受け手の購読が `active` になってからオーナーを切り替え、元の購読を解約する。
- 受け手の購読が `active` になったら、元の購読はすぐに解約し、未使用の期間を日割りで元のオーナーに返金する。二重の課金を残さないため。
- 解約が反映されるまでの短い間は、1 つのプロジェクトに購読が 2 つある。この間は、どちらか 1 つが `active` / `trialing` なら `active` とする。
- 決済の完了後に作成が失敗した場合に備えて、作成はプロジェクト ID について冪等にする。成功画面の再試行と定期ジョブで、「`active` な購読があるのにプロジェクトの行が無い」ものを作り直す。それでも作れなかったものは、運用者が調べて返金する。

### Control Plane 障害時

- 公式ホスト版(`ENTITLEMENT_MODE=control-plane`)では、プロジェクトの状態が分からないとき、作成・書き込み・エクスポートを HTTP 503 で拒否する(fail closed)。障害の間に停止中のプロジェクトを編集・エクスポートできてしまうと、停止の強制が抜けるため。
- 読み取りは続ける。閲覧はどの状態でも許されるので、状態が分からなくても結果は変わらない。
- 状態はキャッシュする。Control Plane が応答で返す有効期間(`maxAgeSeconds`)の間はキャッシュを使う。Control Plane に届かないときは、`staleIfErrorSeconds` の間だけ古い値を使い、それを過ぎたら 503 にする。秒数は、停止状態を強制する story で決める。
- 停止状態を強制する story が出るまでは、ADR-0011 の挙動のままになる。権利を問い合わせるのは作成時だけで、キャッシュはまだ無く、Control Plane に届かなければ作成だけを 503 で拒否する。

### 停止中のエクスポート拒否と法令

- エクスポート機能は、停止中は使えない。
- それとは別に、個人情報保護法の開示請求・消去の請求や、GDPR 第 20 条(データポータビリティ)のような本人からの請求には、運営者が法令に従って個別に応じる。
- 両方を利用規約とプライバシーポリシーに書く。
- 調査メモ: Trello と Atlassian(Jira)の公式ページでは、請求期間の末日まで有効で、データを削除せずに保持する扱いを確認できた。停止後にエクスポートできるかは、どちらの公式ページにも書かれていなかった。

## 未決事項

設計案 v1 の未決事項と、計画レビューで加えたものは、2026-11-14 にすべて決めた(上記の Decision)。キャッシュの秒数と、保持期限を設けるかどうかの見直しだけは、後続の story で決める。

## Consequences

- 判定が「作成時に所有数を比べる」から「操作ごとにプロジェクトの状態を見る」に変わる。プロジェクトに対する書き込み・エクスポートの経路はすべて状態を確認する必要があり、確認漏れがそのまま無料利用になる。
- 「購読なし = `suspended`」なので、開発者自身の既存プロジェクトも、強制を有効にした時点で停止する。有効化の前に手当てする。
- 停止中のエクスポート拒否は、利用規約とプライバシーポリシーに明記するまで本番で有効にしない。
- 譲渡のたびに、元のオーナーへの日割りの返金が発生する。
- Control Plane の障害は、公式ホスト版の書き込みとエクスポートの障害になる。読み取りは続く。
- 解約や未払いは、そのプロジェクトのメンバー全員の編集を止める。オーナー以外にも影響するので、停止の理由と再開の方法を画面で示す。
- 所有上限の変数と `maxOwnedProjects` の判定は不要になる。置き換えは作成フローの story で行う。
- Control Plane では、購読と権利がプロジェクトに紐づく。Checkout は、プロジェクトの作成・再開・譲渡のための購入に作り替わる。Portal は customer 単位のままなので、そのユーザーの全プロジェクトの購読をまとめて扱う。

## Amendment 2026-11-18 (story #433)

停止状態の強制を実装した。経路の一覧は [billing-write-gate.md](../billing-write-gate.md)。

- **強制のスイッチ**: `ENTITLEMENT_MODE=control-plane` かつ `PROJECT_WRITE_ENFORCEMENT=true` のときだけ書き込みを判定する。未設定なら従来どおり何も拒否しない。公開準備(既存プロジェクトの扱いと法務表示)が済むまで本番では設定せず、staging で先に有効にして確認する。セルフホストは設定しても影響を受けない。
- **キャッシュ**: プロジェクトごとに、Control Plane の応答の `maxAgeSeconds` の間だけ使う。取得に失敗したときだけ `staleIfErrorSeconds` の間、古い値を使う。期限の起点は応答を受け取った時刻。本体側に独立した TTL は持たない。現行の Control Plane の値(`ENTITLEMENT_CACHE_TTL_SECONDS=60`、`ENTITLEMENT_STALE_IF_ERROR_SECONDS=300`)では、停止が書き込みに反映されるまでの最大遅延は、Control Plane が正常なら 60 秒、障害中は 360 秒(60 + 300)。ただし、キャッシュは Worker の isolate ごとなので、状態の変化に気づく時刻は isolate ごとに最大 60 秒ずれる。
- **grace**: `validUntil` を過ぎた `grace` は、キャッシュの期限内でも `suspended` として扱う。
- **応答**: `suspended` は HTTP 403 と `code: PROJECT_SUSPENDED`、状態が分からないときは HTTP 503 と `code: ENTITLEMENT_UNAVAILABLE`。MCP は同じ code を含むエラー文、story map のライブ編集は `suspended` / `entitlement_unavailable` の reject code で返す。
- **応答の古い値**: キャッシュは revision が戻る応答を採用しない。
- **脱退**: 現在のコードにメンバー本人が脱退する経路はない。追加するときは書き込みから除外する(経路一覧の例外に記載)。
